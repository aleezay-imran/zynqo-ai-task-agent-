# Implementation Plan: Zynqo AI Backend & MCP Integration

## Project Context

**Project Type**: Next.js 16.4.2 App Router with TypeScript, Prisma ORM 8, PostgreSQL  
**Language**: TypeScript (strict mode)  
**Build System**: Next.js with Turbopack  
**Test Framework**: None configured yet - will use manual testing  
**Build Command**: `npm run build`  
**Test Command**: `npm run dev` + manual browser testing  
**Database**: Prisma-managed PostgreSQL (already migrated)  

**Key Findings from Exploration**:
- Prisma ORM 8 is configured with contract-based schema at `prisma/contract.prisma`
- Prisma client singleton exists at `lib/prisma.ts` but uses old Prisma 7 pattern
- Frontend uses local state management via React Context (`lib/store.tsx`)
- Existing chat API at `app/api/chat/route.ts` uses Google Gemini
- MCP endpoint MUST be at `/mcp` (NOT `/api/mcp`) per project requirements
- Components expect specific data shapes defined in `lib/store.tsx`
- No API routes exist yet - all data is local/mock

**Critical Constraints**:
1. MCP endpoint at `/mcp` using Next.js App Router (not `/api/mcp`)
2. Use Prisma ORM 8 patterns with contract.json import
3. Follow @modelcontextprotocol/sdk v2 HTTP handler patterns
4. TypeScript strict mode - all types must be explicit
5. Match existing component interfaces from `lib/store.tsx`

**Type**: refactor  
**Status**: pending

**Description**: Replace the existing Prisma client singleton with Prisma ORM 8 patterns using contract.json import. The current `lib/prisma.ts` uses Prisma 7 PrismaClient pattern which is incompatible with the migrated Prisma 8 setup that relies on contract files.

3. Verify the contract files exist at `prisma/contract.d.ts` and `prisma/contract.json` (generated by prior migration)

## Feature 2: Create RESTful API Routes

**Type**: feat  
**Status**: pending

**Description**: Implement complete CRUD API routes for Tasks, Events, Documents, and Users using Next.js App Router route handlers. Each resource gets collection endpoints (`/api/{resource}/route.ts`) and item endpoints (`/api/{resource}/[id]/route.ts`) with proper error handling, input validation, and TypeScript types matching the Prisma schema.

**Steps**:
1. Create `lib/types.ts` with API request/response types derived from Prisma schema models (Task, Event, Document, User) matching the shapes expected by frontend components in `lib/store.tsx`
2. Create `app/api/tasks/route.ts` with GET (list all tasks for a user, with optional status/priority filters) and POST (create task with title, description, status, priority, dueDate, userId) handlers using Prisma db.orm.public.Task
3. Create `app/api/tasks/[id]/route.ts` with GET (single task), PUT (update task), DELETE (delete task) handlers with id validation
4. Create `app/api/events/route.ts` with GET (list events for user, with optional date range filter) and POST (create event with title, description, startTime, endTime, location, userId) handlers using Prisma db.orm.public.Event
5. Create `app/api/events/[id]/route.ts` with GET, PUT, DELETE handlers for single event
6. Create `app/api/documents/route.ts` with GET (list all documents for user, with optional search query) and POST (create document with title, content, summary, userId, optionally embedding) handlers using Prisma db.orm.public.Document
7. Create `app/api/documents/[id]/route.ts` with GET, PUT, DELETE handlers for single document
8. Create `app/api/users/route.ts` with GET (list users - admin only placeholder) and POST (create user with email, name, optional password hash) handlers using Prisma db.orm.public.User
9. Create `app/api/users/[id]/route.ts` with GET (user profile), PUT (update user), DELETE (delete user) handlers

**Files**:
- `lib/types.ts` (create)
- `app/api/tasks/route.ts` (create)
- `app/api/tasks/[id]/route.ts` (create)
- `app/api/events/route.ts` (create)
- `app/api/events/[id]/route.ts` (create)
- `app/api/documents/route.ts` (create)
- `app/api/documents/[id]/route.ts` (create)
- `app/api/users/route.ts` (create)
- `app/api/users/[id]/route.ts` (create)

**Acceptance Criteria**:
- All API routes follow RESTful conventions (GET for read, POST for create, PUT for update, DELETE for delete)
- Every route has try-catch error handling with appropriate HTTP status codes (400 for validation errors, 404 for not found, 500 for server errors)
- Request bodies are validated before database operations (required fields checked, types validated)
- Responses return JSON with consistent structure: `{ data: T }` for success, `{ error: string }` for errors
- All routes use the updated Prisma ORM 8 db instance from `lib/prisma.ts`
- TypeScript types are explicit for all request/response shapes

## Feature 3: Implement MCP Server with HTTP Transport

**Type**: feat  
**Status**: pending

**Description**: Create a Model Context Protocol server at `/mcp` (NOT `/api/mcp`) using @modelcontextprotocol/sdk v2 HTTP handler patterns. The server exposes tools for task management, event scheduling, and document operations that AI agents can invoke. Uses stateless HTTP transport with Next.js App Router.

**Steps**:
1. Create `lib/mcp/tools.ts` defining MCP tool schemas using Zod for: create-task (title, description, priority, dueDate, userId), update-task (id, updates object), list-tasks (userId, optional filters), delete-task (id), create-event (title, startTime, endTime, userId, optional description/location), list-events (userId, optional date filters), create-document (title, content, userId, optional summary), search-documents (userId, query string for content search)
2. Create `lib/mcp/handlers.ts` implementing the business logic for each tool using Prisma db operations, matching the same database calls as the REST API routes but wrapped for MCP tool execution format
3. Create `app/mcp/route.ts` as a Next.js App Router route (NOT in /api) implementing POST handler that uses createMcpHandler from @modelcontextprotocol/sdk with McpServer instance, registers all tools from tools.ts, and returns Web-standard Response
4. Configure McpServer with capabilities: { tools: {}, resources: {}, prompts: {} } and metadata { name: "zynqo-mcp-server", version: "1.0.0" }
5. Each tool handler validates input with Zod schema, executes Prisma operation, returns MCP content blocks with success/error status

**Files**:
- `lib/mcp/tools.ts` (create)
- `lib/mcp/handlers.ts` (create)
- `app/mcp/route.ts` (create)

**Acceptance Criteria**:
- MCP endpoint is accessible at `http://localhost:3000/mcp` (not /api/mcp)
- Server responds to MCP protocol requests with proper JSONRPC 2.0 format
- All 8 tools are registered: create-task, update-task, list-tasks, delete-task, create-event, list-events, create-document, search-documents
- Each tool uses Zod for input validation and returns clear error messages for invalid inputs
- Tool responses include MCP content blocks with text or JSON data
- Database operations use the Prisma ORM 8 db instance from `lib/prisma.ts`
- HTTP transport is stateless (sessionIdGenerator: undefined pattern)

**Verification**:

## Cross-Feature Integration & Testing

**Description**: After all features are implemented, perform end-to-end integration testing to ensure the full stack works together - API routes serve data, MCP server executes operations, and frontend components display and persist changes.

**Integration Points**:
1. Prisma client is shared across REST API routes and MCP tool handlers
2. API routes and MCP tools perform equivalent operations on the same database tables
3. Frontend components consume REST API endpoints for CRUD operations
4. Chat interface could invoke MCP tools (future enhancement - not required for this phase)

**Critical Issues to Watch**:
- **User Authentication**: Currently no auth system - using placeholder user IDs. All API routes need userId parameter or hardcoded test user. Future: add NextAuth.js or similar.
- **CORS**: MCP endpoint at /mcp should not need CORS if accessed from same origin. If MCP clients connect from external sources, add CORS headers.
- **Input Validation**: Both REST APIs and MCP tools validate inputs with Zod or manual checks before database operations.
- **Error Handling**: Prisma errors (unique constraints, foreign key violations, not found) must be caught and returned with appropriate status codes/messages.
- **TypeScript Strict Mode**: All imports, types, and function signatures must satisfy TypeScript strict checks - no implicit any.
- **Prisma ORM 8 Migration**: Contract files must exist and be up to date. If schema changes, run `prisma contract emit` to regenerate.
- **Environment Variables**: DATABASE_URL must be set in .env for both dev server and MCP endpoint to connect to PostgreSQL.

**Potential Blockers**:
1. Prisma ORM 8 contract files missing or stale - run `prisma contract emit` and `prisma migrate dev`
2. MCP SDK version compatibility - ensure @modelcontextprotocol/sdk version supports createMcpHandler
3. Next.js App Router route handling for /mcp - verify it's outside /api directory structure
4. TypeScript JSON import syntax requires Node 22.18+ and specific tsconfig settings - verify tsconfig.json has resolveJsonModule: true and appropriate module/moduleResolution

**Testing Checklist**:
- [ ] Prisma client connects to database successfully
- [ ] All REST API endpoints return valid JSON responses
- [ ] MCP endpoint responds to JSON-RPC 2.0 protocol requests
- [ ] MCP tools execute and modify database records
- [ ] Frontend components load data from APIs on mount
- [ ] Frontend create/update/delete operations persist to database
- [ ] Page refresh maintains state (data from database, not local storage)
- [ ] Error messages display for failed operations
- [ ] TypeScript compilation passes with no errors
- [ ] Next.js build completes successfully

## Implementation Notes

**Execution Order**: Features must be implemented strictly in order 1 → 2 → 3 → 4 because:
1. Feature 1 (Prisma client) is a prerequisite for Features 2 and 3
2. Feature 2 (API routes) must exist before Feature 4 can connect to them
3. Feature 3 (MCP server) can be implemented in parallel with Feature 2 (both use Feature 1)
4. Feature 4 (Frontend updates) is the final integration layer

**Testing Strategy**: After each feature, run verification commands before moving to next feature. Do not proceed if verification fails - fix issues immediately.

**Commit Strategy**: Each feature should be a separate commit with descriptive message following Conventional Commits format:
- `refactor(prisma): update to ORM 8 contract pattern`
- `feat(api): add RESTful CRUD routes for tasks, events, documents, users`
- `feat(mcp): implement MCP server with database tools`
- `feat(frontend): connect components to REST API endpoints`

**Rollback Plan**: If any feature fails, revert the commit and fix issues before retrying. The Prisma ORM 8 client update (Feature 1) is most critical - if it fails, the entire implementation is blocked.
